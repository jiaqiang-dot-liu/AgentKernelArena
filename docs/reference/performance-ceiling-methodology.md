# Performance ceiling methodology

This methodology defines how an `image_kernel` task assigns a performance-bound
label and estimates `mean_case_latency_ms`. The result is a hardware-aware lower
bound on latency for the task's scored cases. It is not the latency of the
original implementation and is not a promise that a known implementation already
achieves the bound.

## Required output

Each analyzed task records a `performance_ceiling` object in `config.yaml` with:

- `bound`: one of `compute-bound`, `memory-bound`, `latency-bound`, or
  `mixed-bound`.
- `mean_case_latency_ms`: the arithmetic mean of the per-case ideal latencies.
- `cases`: the ideal latency and the workload quantities used for each scored
  case.
- `methodology`: the hardware assumptions, profiler, formula, and evidence needed
  to reproduce the estimate.

The per-case values are authoritative. The mean is derived from them and must not
be measured or maintained independently.

## Analysis scope

The timing boundary must match the task's scored operator boundary. Include every
kernel, synchronization point, reduction, and data movement operation required to
produce the validated outputs. Exclude input construction, JIT compilation,
warmup, and correctness-only work.

Use the exact shapes, dtypes, layouts, and output contract from
`session_cases.json`. A ceiling calculated for a different shape or a weakened
correctness contract is invalid.

The ideal implementation may use any optimization that is legal for the task,
including shape-based dispatch and kernel fusion. It must not dispatch on case
IDs, use test-specific constants that are not properties of the input shape, skip
required outputs, or rely on data values known only to the benchmark.

## Per-case latency model

For case \(i\), calculate:

\[
T_{\mathrm{compute},i} =
\frac{O_i}{P_{\mathrm{effective}}}
\]

\[
T_{\mathrm{memory},i} =
\frac{B_i}{BW_{\mathrm{effective}}}
\]

\[
T_{\mathrm{ideal},i} =
T_{\mathrm{latency},i}
+ \max(T_{\mathrm{compute},i}, T_{\mathrm{memory},i})
\]

where:

- \(O_i\) is the minimum arithmetic work required by a legal implementation.
- \(B_i\) is the minimum semantic data movement required by a legal
  implementation, not necessarily the traffic generated by the current code.
- \(P_{\mathrm{effective}}\) is the applicable compute throughput for the
  operation's dtype and instruction family.
- \(BW_{\mathrm{effective}}\) is the applicable memory-level bandwidth.
- \(T_{\mathrm{latency},i}\) covers irreducible device dispatch, dependency,
  barrier, and synchronization latency that cannot overlap the dominant resource
  term.

Use calibrated microbenchmark throughput when available. A hardware specification
may be used for a theoretical ceiling, but the source and value must be recorded.
Do not mix a marketing compute peak with a calibrated memory peak without
documenting that choice.

For a composite operator, build the minimum legal execution graph first. Sum
serial stages and use the maximum only for stages that can execute concurrently.
Do not assume that CUDA or HIP Graph capture fuses kernel nodes. Graph capture
removes repeated host submission overhead, while each device kernel still has
dispatch and execution latency.

## Semantic work and traffic

Derive operation count and semantic traffic from the operator contract:

1. Count the input bytes that a correct ideal implementation must read.
2. Count all required output bytes.
3. Include mandatory intermediate traffic only when no legal fusion or on-chip
   retention strategy can eliminate it.
4. Count arithmetic operations according to the instruction family used by the
   hardware ceiling.
5. Record assumptions for sparsity, masking, quantization metadata, atomics, and
   reductions.

Profiler-reported HBM traffic describes the profiled implementation. It is useful
for diagnosing that implementation, but it must not automatically replace
semantic traffic in the ideal model.

## Device latency calibration

Measure the device dispatch floor on the same GPU, software stack, and timing
path as the task:

1. Warm up all modules and kernels before collection.
2. Profile a trivial or near-empty kernel node from the same runtime stack.
3. Collect at least 20 dispatches.
4. Use the minimum stable duration after excluding initialization and JIT
   activity.
5. Confirm that repeated collections produce the same floor within normal clock
   variation.

The dispatch floor is device-side latency. It remains relevant when the task uses
CUDA or HIP Graph timing because graph replay does not merge the graph's kernel
nodes.

## Profiling procedure

Run every scored case using the task's normal correctness and benchmark paths.
Record the uninstrumented CUDA or HIP Graph latency first. Profiling instrumentation
can alter inter-kernel gaps and must not replace the task's benchmark result.

Use `rocprofv3` or `rocprof-compute` to collect:

- Kernel names, dispatch count, duration, grid size, and workgroup size.
- VGPR, SGPR, LDS, scratch, and occupancy information.
- VALU and MFMA utilization for compute analysis.
- HBM, cache, and memory-stall metrics for memory analysis.
- Barrier, atomic, LDS conflict, and dependency evidence where relevant.

Collect incompatible hardware counter groups in separate runs. Use the same case
and warmed binary for every pass.

## Bound classification

Assign the label from the ideal model and confirm it with profiler evidence:

- `compute-bound`: \(T_{\mathrm{compute}}\) dominates, and the relevant VALU or
  MFMA pipeline is the limiting resource.
- `memory-bound`: \(T_{\mathrm{memory}}\) dominates, and the relevant memory level
  limits progress.
- `latency-bound`: dispatch, synchronization, dependency, or insufficient
  parallelism dominates both compute and memory service time.
- `mixed-bound`: no single component clearly dominates across the scored cases.

Low compute utilization alone does not prove memory-bound behavior. Low memory
stall alone does not prove compute-bound behavior. Small grids can show low values
for both because the operator is latency-bound.

If different cases have different dominant bounds, use `mixed-bound` at task level
and retain the per-case labels in the task analysis.

## Mean ideal latency

AgentKernelArena scores these `image_kernel` tasks with an arithmetic mean across
cases, so the ceiling uses the same aggregation:

\[
\texttt{mean\_case\_latency\_ms} =
\frac{1}{N}\sum_{i=1}^{N} T_{\mathrm{ideal},i}
\]

The corresponding aggregate efficiency is:

\[
E =
\frac{\texttt{mean\_case\_latency\_ms}}
     {\texttt{agent\_mean\_case\_latency\_ms}}
\times 100\%
\]

Do not average per-case percentages when reporting this aggregate. A
production-weighted metric may be added separately, but it must not replace the
equal-weight Arena metric.

## Validation and maintenance

Record the GPU architecture, software stack, profiler, bandwidth or compute
ceilings, dispatch floor, formula, and per-case inputs. Recalculate the ceiling
when any of the following changes:

- Scored cases, dtypes, layouts, or correctness tolerances.
- GPU architecture, partitioning mode, clocks, or runtime stack.
- Timing boundary or benchmark method.
- Task edit surface or rules governing legal fusion and dispatch.
- A valid implementation measures faster than the recorded ceiling.

An efficiency above 100% is a ceiling invalidation signal. Do not silently clamp
it; inspect the assumptions and publish a corrected ceiling.
